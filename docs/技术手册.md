## 1. 系统概览

### 1.1 组成

工程由两个控制器组成，通过一路 UART 双向通信：

- **STM32F103C8T6 飞控**：BMI088 姿态解算、起飞检测、上升段姿态保持、下降段视觉引导、四路舵机 PWM、握手与 50 Hz 遥测。
- **OpenMV 视觉端**：绿色目标识别、偏移量上行、遥测解析与屏幕叠加、原生图像录像与遥测 CSV 记录。

控制对象为带 **X 型尾翼、四舵机** 的小型飞行器。一次飞行的时间线：

```text
上电 → IMU 静止标定 → 舵机回中 → 等待起飞 → 起飞检测
     → 上升段（保持 yaw/roll，pitch 两阶段补偿，可选视觉 yaw）
     → 下降段（视觉前视追踪引导 pitch/yaw，roll 保持）
```

### 1.2 能力与边界

| 能力 | 实现情况 |
|---|---|
| 双 MCU 双向串口通信 | 有，115200 8N1，CRC8 校验 |
| 视觉目标识别与偏移输出 | 有，OpenMV 绿色色块 + 跟踪 ROI |
| 姿态解算 | 有，BMI088 + 四元数 EKF |
| 起飞检测 | 有，去重力机体 X 轴加速度 + 连续确认 |
| 上升段姿态保持 | 有，yaw/roll 保持起飞姿态；pitch 补偿到目标角后锁存 |
| 上升段视觉 yaw | 有，识别到目标时 yaw 切视觉，脱锁回自稳 |
| 下降段视觉引导 | 有，前视追踪 + 视觉 PID + X 尾混控 |
| 飞行状态遥测 | 有，45 字节、50 Hz、460800 波特率（含 LOS 增量、四路舵机角、加速度与 PN 调试量） |
| 模式握手 | 有，下位机决定 default/pitch/yaw/both |
| 机载录像 / 遥测记录 | 有，ImageIO 原生流 + 逐帧 CSV |
| 地面站 / 无线链路 | **没有** |
| GPS / 磁力计 / 测距 / 空速 | **没有** |
| 着陆检测 / 失控保护 / 目标搜索 | **没有** |

### 1.3 八条关键结论

1. 当前协议是 **45 字节遥测 + 8 字节视觉帧 + 5 字节握手 / 4 字节 ACK / 4 字节复位**，旧版本文档中的 10/14/37 字节帧已不存在。
2. 遥测发送的启动条件是 **收到 OpenMV 的握手 ACK**（`attitude_tx_armed`），不是“收到第一帧视觉帧”；OpenMV 上电会先发复位帧清除该标志。
3. OpenMV **必须先完成握手才进入主循环**，单独给 OpenMV 上电会停在 `waiting handshake...`。
4. PID 的微分项使用 **BMI088 陀螺角速度**（`Dout = -Kd × 角速度`），不是对角误差求导；`DART_PID_OLS_ORDER = 0`。
5. 视觉滤波默认 **RAW_RATE**：位置角不做低通，只用当前帧的 `atan`；角速率做一阶低通。原 EKF 通过 `DART_VISION_FILTER_MODE` 可切回。
6. 上升段 pitch 采用两阶段：未低头到目标角时输出固定抬升 100 µs，低头后转 PID 闭环；回到目标角后锁存为 0。
7. 下降段脱锁后**回发射航向**（`DART_YAW_ABS_LOCK_ENABLE = 0`，当前关闭）。功能本身保留：置 1 后在 `|视线偏航角|` 创新低时记录当前 `yaw` 作为最佳航向，脱锁后按该角做 PID；关闭时 `yaw_unlock_output()` 直接回退 `calculate_yaw_hold()`。
8. `main()` 只初始化 GPIO / SPI1 / TIM2 / USART1；USB、USART3、TIM3 的函数仍在文件中但不再调用，`defaultTask` 已删除，共 3 个任务。

## 2. 硬件平台与接线

### 2.1 主控

| 项目 | 配置 |
|---|---|
| MCU | STM32F103C8T6，LQFP48 |
| 内核 / 主频 | Cortex-M3，72 MHz（HSE 12 MHz × 6） |
| Flash / RAM | 64 KB / 20 KB |
| HAL 时基 | TIM1 更新中断（`stm32f1xx_hal_timebase_tim.c`） |
| RTOS | FreeRTOS 10.0.1，CMSIS-RTOS v2，tick 1 kHz，heap_4，10 KB |
| 工具链 | Keil MDK，ARMCC V5.06（最近构建日志为 update 6 build 750） |
| CubeMX | 6.18.1，`MA_DartGuide.ioc` |

### 2.2 引脚分配

来自 `gpio.c` / `tim.c` / `usart.c` / `spi.c` / `main.h`：

| 功能 | 引脚 | 说明 |
|---|---|---|
| 舵机 PWM 1–4 | PA0 / PA1 / PA2 / PA3 | TIM2 CH1–CH4，200 Hz |
| RGB LED 红 / 绿 / 蓝 | PA4 / PA5 / PA6 | 低电平点亮（`DART_LED_ACTIVE_LEVEL`） |
| 视觉串口 TX / RX | PA9 / PA10 | USART1，115200 8N1 |
| IMU SPI SCK / MISO / MOSI | PB3 / PB4 / PB5 | SPI1 重映射，MISO 上拉 |
| 陀螺 CS / INT | PB12 / PB13 | INT 配置为上升沿中断，控制中未使用 |
| 加速度 CS / INT | PB14 / PB15 | INT 配置为上升沿中断，控制中未使用 |
| USB DM / DP | PA11 / PA12 | 不再初始化，`usb.c` 仍参与编译 |
| USART3 | PB10 / PB11 | `usart.c` 保留初始化函数，`main()` 不调用 |
| CAN | PB8 / PB9 | GPIO 与重映射仍配置，无 CAN 外设初始化 |

TIM2 时基：预分频 71（1 MHz 计数）、周期 4999，即 5 ms / 200 Hz。
频率上限由行程决定：最大脉宽 2550 µs 要求周期大于 2550 µs，即不高于约 392 Hz；
实际可用值还受舵机型号限制（模拟舵机通常只支持 50–70 Hz，数字舵机常见上限 333 Hz）。

### 2.3 舵机索引与通道映射

`set_servo_compare()` 的索引与定时器通道不是顺序对应的，换线或改混控前必须核对：

| 索引 | 定时器通道 | 引脚 |
|---|---|---|
| 0 | TIM2_CH3 | PA2 |
| 1 | TIM2_CH2 | PA1 |
| 2 | TIM2_CH1 | PA0 |
| 3 | TIM2_CH4 | PA3 |

### 2.4 与 OpenMV 的接线

| OpenMV | F103 | 方向 |
|---|---|---|
| UART3 TX（常见 P4） | PA10 / USART1_RX | OpenMV → F103，视觉帧 |
| UART3 RX（常见 P5） | PA9 / USART1_TX | F103 → OpenMV，握手 + 遥测 |
| GND | GND | 必须共地 |

双方均为 3.3 V TTL，不要接 RS232 电平。具体 UART3 引脚以所用 OpenMV 型号为准。

### 2.5 电源与执行机构

- 四路舵机由 TIM2 输出 200 Hz PWM，中位 1550 µs，行程 550–2550 µs。
  满舵 2550 µs 时占空 51%、低电平仅 2450 µs，已到模拟舵机边界。
- 每个控制周期（2 ms）脉宽变化限制 30 µs，即 15 µs/ms；跨满 ±1000 µs 行程约需 133 ms。
- CCR 已开预装载（`HAL_TIM_PWM_ConfigChannel` 置 `OCxPE`），新脉宽只在 update 事件生效，
  因此实际执行刷新率等于 PWM 频率，而不是控制环的 500 Hz。
- 首次测试必须拆除动力或牢固约束机体，先确认中位、方向、限位与 LED，再上动力。
- BMI088 上电做 6000 点静止零偏标定；标定期间机体必须完全静止。

## 3. 软件架构与启动时序

### 3.1 分层

```text
┌──────────────────────────── OpenMV ────────────────────────────┐
│ main.py                                                        │
│  传感器初始化 → 等待握手 → 目标识别 → 视觉帧 → 遥测解析        │
│  → 屏幕叠加 → ImageIO 录像 + 遥测 CSV                          │
└───────────────────────────┬────────────────────────────────────┘
                            │ UART3 / USART1，115200 8N1
┌───────────────────────────┴────────────────────────────────────┐
│ STM32F103                                                      │
│  Core: HAL / 时钟 / FreeRTOS                                   │
│  ins_task.c: BMI088 → QuaternionEKF → INS                     │
│  Control_Task.c: 状态机 / 视觉滤波 / 引导 / PID / 混控 / 遥测   │
│  bsp: DWT 计时、PWM、LED、UART 中断                            │
│  TIM2 → 四路舵机                                               │
└────────────────────────────────────────────────────────────────┘
```

### 3.2 FreeRTOS 任务

| 任务 | 优先级 | 栈 | 周期 | 工作 |
|---|---|---:|---|---|
| `IMU_Task`（`Ins_Task`） | Normal | 2048 B | 1 ms | BMI088 初始化与标定（失败每 100 ms 重试）、`INS_Task()` |
| `Control_Task`（`CTL_Task`） | Normal | 1024 B | 2 ms | `control_Task()` 状态机与控制 |
| `led_task`（`LED_Task`） | Low | 512 B | 20 ms | LED、50 Hz 遥测、100 ms 握手 |

- IMU 与 CTL 同优先级，实际执行顺序由 1 ms tick 时间片轮转决定；INS 快照用关中断 `memcpy` 保证一致性。
- 三个任务栈都从 10 KB FreeRTOS heap 动态分配；主栈 2 KB、传统 heap 512 B 也计入 RAM。

### 3.3 数据流

```text
BMI088 ──SPI1──> INS_Task ──INS──> Control_Task ──TIM2 PWM──> 四舵机
                                      ▲
OpenMV 视觉帧 ──USART1 IRQ──> mailbox ┘
                                      │
Control_Task ──50 Hz 遥测──> USART1 IT ──> OpenMV 显示 / 录像 / CSV
```

### 3.4 启动时序

1. F103 上电：`HAL_Init()`、`SystemClock_Config()`（HSE 12 MHz × 6 = 72 MHz），依次调用 `MX_GPIO_Init()`、`MX_SPI1_Init()`、`MX_TIM2_Init()`、`MX_USART1_UART_Init()`，再 `DWT_Init()`；随后 `osKernelInitialize()` + `MX_FREERTOS_Init()` 创建 3 个任务。
2. `IMU_Task` 先 `control_notify_imu_ready(0)`，然后循环 `BMI088_init(&hspi1, 1U)`（每 100 ms 重试，含 6000 点静止标定），成功后 `INS_Init()`、`INS_Task()`，置 `imu_ready = 1`，进入 1 ms 姿态循环。
3. `Control_Task` 执行 `control_Init()`：清空运行时结构（保留 IMU 标志）、初始化 5 个 PID、计算一次焦距、启动 USART1 单字节中断接收、状态置 `READY`。
4. `LED_Task` 每 20 ms 调用 `led_Task()`、`attitude_telemetry_send()`、`openmv_handshake_send()`。
5. OpenMV 上电：`init_sensor()`，然后 `wait_for_handshake()`——连发 3 次复位帧 `5B 5B 5B CRC`，清空接收缓冲，等待 `A5` 握手帧。
6. F103 每 100 ms 发一次握手（armed 前）；OpenMV 收到合法握手后回 3 次 ACK `5A MODE FE CRC`，清空缓冲并进入主循环。
7. F103 收到 ACK 后 `attitude_tx_armed = 1`，开始 50 Hz 遥测；OpenMV 主循环开始发视觉帧。
8. IMU 就绪后，F103 在 `IMU_READY` 等 500 ms，启动 TIM2 PWM、四舵回中，进入 `SERVO_READY` 等待起飞。

## 4. 通信协议

### 4.1 物理层

| 项目 | 值 |
|---|---|
| 波特率 | 115200 |
| 数据位 / 停止位 / 校验 | 8 / 1 / None |
| 流控 | 无 |
| OpenMV 端口 | `UART(3)`，`read_buf_len = 2048` |
| F103 端口 | USART1，PA9 / PA10，中断优先级 5 |
| 字节序 | 所有多字节整数为**大端** |

### 4.2 CRC8

三个协议共用同一实现：初值 `0x00`、多项式 `0x8C`、反射（LSB-first），与 `main.py` 的 `crc8_lsb()` 完全一致。

```text
crc = 0x00
for byte in data:
    crc ^= byte
    for _ in range(8):
        crc = ((crc >> 1) ^ 0x8C) & 0xFF if crc & 1 else crc >> 1
```

覆盖范围：视觉帧字节 0..6，遥测帧字节 0..35，握手帧字节 0..3，ACK 与复位帧字节 0..2。

### 4.3 握手、ACK 与复位

| 方向 | 帧格式 | 长度 | 触发 |
|---|---|---|---|
| F103 → OpenMV | `A5 MODE FLAGS FE CRC8` | 5 B | 每 100 ms，直到收到 ACK |
| OpenMV → F103 | `5A MODE FE CRC8` | 4 B | 收到合法握手后连发 3 次 |
| OpenMV → F103 | `5B 5B 5B CRC8` | 4 B | 上电时连发 3 次，清除握手锁存 |

- `MODE`：0 default、1 pitch-only、2 yaw-only、3 both；F103 用编译期宏 `DART_MODE`（默认 `DART_MODE_BOTH`）。
- `FLAGS`（握手帧）bit0 = IMU 就绪。
- F103 只在 ACK 的 `MODE` 与自身 `DART_MODE` 相同、且 CRC 正确时置 `attitude_tx_armed = 1`；复位帧可将其清 0，从而允许重新握手。
- 握手使用阻塞发送（超时 5 ms），只在 armed 前发生。

### 4.4 视觉上行帧（OpenMV → F103，8 字节）

```text
AA  xH xL  yH yL  recognized  FF  CRC8
```

| 字节 | 内容 |
|---|---|
| 0 | `0xAA` |
| 1-2 | X 偏移，int16 大端，相对制导中心，向右为正 |
| 3-4 | Y 偏移，int16 大端，相对制导中心，向下为正 |
| 5 | `recognized`：1 = 识别到目标，0 = 未识别 |
| 6 | `0xFF` |
| 7 | CRC8（覆盖 0..6） |

- 制导中心由 OpenMV 的 `GUIDE_CX/GUIDE_CY` 决定（当前 `(160, 120)`）；F103 以 `(0, 0)` 为中心，不保存像素坐标。
- 偏移超过 `|dx| ≤ 160`、`|dy| ≤ 120` 时按无目标处理。
- 未识别时发送 `x = 0, y = 0, recognized = 0`。
- OpenMV 在 `uart.txdone()` 为假时直接丢帧并累加 `TX_SKIP_COUNT`，不做排队。

### 4.5 遥测下行帧（F103 → OpenMV，45 字节，50 Hz，波特率 460800）

```text
55  gxH gxL gyH gyL gzH gzL
    pH  pL  yH  yL  rH  rL
    oPH oPL oYH oYL oRH oRL
    mode state flags
    losYawH losYawL losPitchH losPitchL
    s1H s1L s2H s2L s3H s3L s4H s4L
    dbgFlags
    aMeasH aMeasL  aCmdH aCmdL
    pnOmegaH pnOmegaL  yawUH yawUL
    FE CRC8
```

| 字节 | 内容 | 单位 |
|---|---|---|
| 0 | `0x55` | — |
| 1-2 | 陀螺 X | 0.1 °/s |
| 3-4 | 陀螺 Y | 0.1 °/s |
| 5-6 | 陀螺 Z | 0.1 °/s |
| 7-8 | 当前 pitch | 0.01° |
| 9-10 | 当前 yaw | 0.01° |
| 11-12 | 当前 roll | 0.01° |
| 13-14 | 输出目标 pitch | 0.01° |
| 15-16 | 输出目标 yaw | 0.01° |
| 17-18 | 输出目标 roll | 0.01° |
| 19 | mode（0..4，4 = debug） | — |
| 20 | state（0..7，7 = debug） | — |
| 21 | flags | — |
| 22-23 | LOS yaw 增量（相对上电 1 s 参考角） | 0.01° |
| 24-25 | LOS pitch 增量（同上） | 0.01° |
| 26-27 | 舵机 1 角度 | 0.1° |
| 28-29 | 舵机 2 角度 | 0.1° |
| 30-31 | 舵机 3 角度 | 0.1° |
| 32-33 | 舵机 4 角度 | 0.1° |
| 34 | 调试标志：bit0 参考角已捕获 | — |
| 35-36 | `a_meas`：加速度计实测偏航侧向加速度 | 0.01 m/s² |
| 37-38 | `a_cmd`：PN 给出的加速度指令 | 0.01 m/s² |
| 39-40 | `pn_omega`：PN 用的视线角速率（未钳位） | 0.01 °/s |
| 41-42 | `yaw_u`：yaw 通道舵面输出（混控前） | 1 µs |
| 43 | `0xFE` | — |
| 44 | CRC8（覆盖 0..43） | — |

当前姿态角按 `DART_INS_*` 映射：`pitch = -INS.Roll`、`roll = INS.Pitch`、`yaw = INS.Yaw`；陀螺通道为原始机体轴 X/Y/Z。

flags 位定义：

| 位 | 名称 | 含义 |
|---|---|---|
| bit0 | `DART_ATT_FLAG_LINK_VALID` | 250 ms 内有有效视觉帧 |
| bit1 | `DART_ATT_FLAG_TARGET_VALID` | 目标仍有效（120 ms 保持窗口内） |
| bit2 | `DART_ATT_FLAG_IMU_READY` | IMU 已完成初始化与标定 |
| bit3 | `DART_ATT_FLAG_HANDSHAKE_DONE` | 已收到 ACK，armed |
| bit4 | `DART_ATT_FLAG_OUTPUT_VALID` | 输出目标角有效（上升/下降段） |
| bit6 | `DART_ATT_FLAG_DBG_ALWAYS_ON` | **固件版本标记**：本版把制导调试量改成每周期更新（2026-11-18 22:39 起）。看到 flags 含 0x40 才说明烧的是这一版；缺这一位时 `a_meas/pn_omega/yaw_u` 在地面/DEBUG 态恒为 0 |

> **调试模式（MODE=4 / STATE=7）**：编译期把 `DART_MODE` 设为 `DART_MODE_DEBUG`。
> 不做起飞检测、不驱动舵机（PWM 保持中位），只运行视觉引导并上报；
> 上电 1 s 后的静止姿态作为 LOS 增量的零点；舵机角按 1550 µs=0°、±1000 µs=±90° 换算。
> 该模式下 OpenMV 仍正常显示，并照常启动录像与 CSV 记录；因为没有发射也没有落地标志，
> 录像只在 `MAX_RECORD_MS = 30 s` 的绝对上限处停止（见 6.5）。

### 4.6 发送时序与调度

- 遥测固定在 `LED_Task` 中每 20 ms 发一帧，使用 `HAL_UART_Transmit_IT` + 静态缓冲。
- 发送前检查 `huart1.gState == HAL_UART_STATE_READY`；上帧未发完则跳过本帧，避免覆盖缓冲。
- 遥测与握手同用 USART1，波特率 **460800**（2026-11-18 由 115200 提高，给新增的 8 字节调试量留余量）。握手仅在 armed 前发送，正常飞行时总线上只有 45 字节遥测和 8 字节视觉帧。

### 5.2 IMU 与姿态

`INS_Task()` 每 1 ms 执行一次：

1. `BMI088_Read()` 读取加速度与角速度，复制到全局 `INS`。
2. `IMU_QuaternionEKF_Update()` 用陀螺与加速度融合，更新 `INS.Yaw/Pitch/Roll`。
3. 把导航系重力转到机体系并相减，得到去重力加速度，再经一阶低通（`AccelLPF = 0.0085`）得到 `INS.MotionAccel_b`。
4. `dt` 异常（`<= 0` 或 `> 20 ms`）时回退 1 ms。

轴映射只在 `ctl_task.h` 处理一次：

```c
DART_INS_PITCH_DEG(ins)   → -(ins->Roll)
DART_INS_ROLL_DEG(ins)    → ins->Pitch
DART_INS_YAW_RATE_RAD_S   → Gyro[2]
DART_INS_PITCH_RATE_RAD_S → -Gyro[1]
DART_INS_ROLL_RATE_RAD_S  → Gyro[0]
```

阅读或修改控制代码时不要在混控处再次交换 pitch 与 roll。

**BMI088 标定**：`BMI088_init(..., 1U)` 执行 6000 点静止采样，计算陀螺零偏；期间机体必须静止。寄存器读回失败时直接返回错误码，由 `IMU_Task` 每 100 ms 重试，因此“没插 IMU / SPI 松动”表现为 LED 停在蓝灯并循环重试，而不是静默卡死。

### 5.3 控制初始化

`control_Init()`：

1. 关中断清空 `DartControl`（保留 `imu_ready`）。
2. 只计算一次焦距：`VisionFocalPx = DART_CAMERA_FOCAL_PX`（当前读出窗口 1280×960，取 480 px；见 7.6.1）。
3. 舵机遥测初值置中位 1550 µs。
4. 初始化 5 个 PID：yaw / pitch 各有“自稳”和“视觉”两套参数，roll 一套。
5. 状态置 `READY`，记录 `last_control_ms` 与 `control_start_ms`。
6. `vision_uart_init()`：中止旧接收、清 ORE、启动单字节中断接收。

`servo_Init()` 启动 TIM2 四路 PWM 并回中；四路全部启动成功才置 `servo_ready`。

### 5.4 状态机

```text
READY ──IMU ready──> IMU_READY ──2 s yaw 零偏标定 + PWM 启动成功──> SERVO_READY
      ──起飞加速度确认 5 周期──> LAUNCHED ──采 5 帧 + 250 ms──> ASCENT
      ──pitch < 5° 连续 25 周期且已上升 300 ms──> DESCENT
      ──合成角速率 > 500 °/s（或 > 400 连两帧）──> LANDED（停 PWM，舵机自由）
```

`DART_STATE_VISION_ERROR` 不是飞行阶段，只在起飞前视觉链路异常时覆盖对外显示状态（LED 闪白）。

`set_state()` 同时更新时间戳 `state_enter_ms`，各种等待与确认门槛都基于它。

各状态进入条件：

| 转换 | 条件 |
|---|---|
| `READY → IMU_READY` | `imu_ready = 1` |
| `IMU_READY → SERVO_READY` | 已完成 2 s yaw 零偏标定且 `servo_Init()` 成功 |
| `SERVO_READY → LAUNCHED` | `DART_LAUNCH_X_SIGN × MotionAccel_b[0] ≥ 22.0` 连续 5 周期 |
| `LAUNCHED → ASCENT` | 姿态采样满 5 帧且已等待 250 ms |
| `ASCENT → DESCENT` | 已上升 ≥ 300 ms，且映射后 pitch < 5° 连续 25 周期（约 50 ms） |
| `DESCENT → LANDED` | 三轴合成角速率 > 500 °/s，或 > 400 °/s 连续两周期；进入后 `HAL_TIM_PWM_Stop` 关闭四路 PWM，舵机失去信号自由转动 |

### 5.4.1 上电 yaw 零偏标定

进入 `IMU_READY` 后先静止采集 2 秒，测出 yaw 的漂移并补偿，再初始化舵机：

```text
采集期总漂移 drift = wrap_180(yaw_end − yaw_start)
漂移速率 bias_dps  = drift / 2.0 s
补偿量             = drift + bias_dps × 标定结束后的经过时间
```

补偿应用在两个地方，**保证控制与遥测一致**：

- `control_Task()` 的 IMU 快照拷贝之后：`ins_snapshot.Yaw = 补偿后角度`
- `attitude_telemetry_send()` 的 `yaw_deg`

两个保护：

| 情况 | 处理 |
|---|---|
| 采集期平均 `abs(gz)` > `DART_YAW_CALIB_MAX_RATE_RAD_S`（2.9 °/s） | 判定为有人在动，放弃本次标定，不补偿 |
| `abs(bias_dps)` < `DART_YAW_CALIB_MIN_DPS`（0.2 °/s） | 漂移可忽略，清零不补偿 |

上电后必须保持静止 2 秒，LED 绿色常亮表示正在标定；变成青色（`SERVO_READY`）才算完成。

### 5.5 起飞检测

```c
launch_accel = DART_LAUNCH_X_SIGN * ins_snapshot.MotionAccel_b[0];
if (launch_accel >= DART_LAUNCH_ACCEL_THRESHOLD) 计数 +1; 否则清零;
```

计数达到 5 才确认起飞。确认后：复位全部 PID、清空姿态累加与各段标志、用当前姿态作为起飞参考、进入 `LAUNCHED` 并立刻执行一次上升段控制。

进入 `LAUNCHED` 后连续采集 5 帧姿态：yaw 用圆均值（`atan2(Σsin, Σcos)`，处理 ±180° 跳变），pitch/roll 用算术平均。

### 5.6 上升段控制

`run_ascent_stabilization()` 每 2 ms 执行，三条轴独立处理。

**yaw**：若 `DART_MODE != PITCH` 且目标有效，走视觉 yaw：

```text
camera_yaw_rate = DART_CAMERA_YAW_SIGN × 视觉角速率 + 机体 yaw 角速率
yaw_command     = LOS_yaw + T_d × camera_yaw_rate
                  （再乘 cos(roll) 投影到机体 yaw 轴，限幅 ±20°）
输出            = 视觉 PID(yaw_command, gz)      ← 与自稳同一个表达式，无额外符号
```

**注意角速率公式里只有相机项乘符号**：机体 yaw 角速率本来就在 INS 系，直接相加。
若整条括号一起乘（旧写法），机体转动补偿会被反号，静止目标下算出来是 −2ψ̇ 而不是 0。

视觉激活/退出各复位一次 `yaw_vision_pid`，避免积分残留。目标失效时立即回到起飞 yaw 自稳，输出目标角报告为 `launch_yaw_deg`。

**pitch**：三种策略，由 `DART_ASCENT_PITCH_MODE` 编译期选择。

| 模式 | 阶段 1 | 阶段 2 | 阶段 3 |
|---|---|---|---|
| `DART_PITCH_MODE_HOLD` (0) | — | 不补偿也不自稳，pitch 输出恒为 0 | — |
| `DART_PITCH_MODE_LIFT_PID` (1)（默认） | 固定抬升 100 µs，直到 `pitch < DART_ASCENT_PITCH_TARGET_DEG`（30°） | **角度+速率串级**（方案 B）：`rate_cmd = GAIN×(pitch−23°)` 限幅 ±35 °/s，`output = KD×(gy − rate_cmd)` | 抬回 23° 即锁存，输出 0 |
| `DART_PITCH_MODE_LIFT_BANG` (2) | 固定抬升，直到 `pitch < 目标角` | 固定抬头 `DART_ASCENT_PITCH_PULL_US`，直到 `pitch ≥ DART_ASCENT_PITCH_STOP_DEG` | 到达即锁存，输出 0 |

`LIFT_BANG` 全程开环，`pitch_pid` 一次都不调用；`LIFT_PID` 的阶段 2 走速率环，同样不调用 `pitch_pid`（该 PID 只保留结构，每轮 `reset_pid` 保持干净）。
两个阶段分别由 `ascent_pitch_below_target`（阶段 1→2）和 `ascent_pitch_done`（阶段 3）表示。

**阶段 3 的锁存条件必须带方向。** `ascent_pitch_done` 只在「阶段 2 已经跑到停止角以下、
又被抬回停止角」时才置位，用 `ascent_pitch_below_stop` 记录方向。
如果只判 `pitch >= STOP`，发射后低头穿过 `[STOP, TARGET)` 区间的那一帧会同时满足
「低于目标角」和「高于停止角」，当场锁存，阶段 2 一次都不执行。

这个缺陷在 11.14 真实发生过：`DART_ASCENT_PITCH_TARGET_DEG` 从 23 改成 30 之后，
发射瞬间 pitch 从 ~40° 一帧掉到 ~26°，直接落进 `[23, 30)` 区间。

| 架次 | `outP` 取值 | 阶段 2 帧数 | 补偿持续到 |
|---|---|---:|---:|
| 00001–00004 | 0.0 / **23.0** | 16~23 | 0.32~0.46 s |
| 00005–00014 | 0.0 / **30.0** | **0** | **0.06~0.07 s** |

00005 之后整个上升段俯仰通道恒为 0，等于完全没有补偿——23° 改成 30° 反而把它关掉了。
修复后按实测 pitch/gy 回放，阶段 2 会跑 13~21 帧（0.43~0.70 s），输出峰值 375~562 µs
（34~51°），比旧构建实测的 234~378 µs 略大，因为介入时机更早、gy 还在峰值。

**`DART_ASCENT_PITCH_STOP_DEG` 两种策略共用**：BANG 拿它当固定抬头的终止角，LIFT_PID 拿它当速率环的角度基准和停止判据。
11.12 全部 15 发实测，固定 110 µs 时 done 瞬间角速率还有 −82~−152 °/s，靠惯性冲到 36~53°，过冲 +6~+23°。

**方案 B 为什么这么改**：11.12 阶段 2 的 350 帧里，gy 从 +190 一路变到 −130 °/s，平均接近 0——
不是稳，是「先猛冲再猛回」，中间那段大角速度全浪费了。固定 110 µs 不看 gy：gy=190 时给 110，
gy=−130 时还是给 110，该刹车时力度不够、该松手时还在推。
改成速率环后，力度随姿态连续变化（target=23°、KD=2.0 的工作点）：

| pitch | gy | 输出 |
|---:|---:|---:|
| 22 | 150 | +302 µs |
| 20 | 120 | +246 µs |
| 15 | 80 | +176 µs |
| 10 | 40 | +106 µs |
| 8 | 20 | +70 µs |

11.12 的 680 帧回放：平均 197 µs（固定方案是 110），3% 打满 420。

误差项取 `gy − rate_cmd` 而不是 `rate_cmd − gy`：`gy` 与 `rate_cmd` 都是「低头为正」，
而舵面是「抬头为正」，两者正方向相反。用「实际 − 期望」取值后，`rate_err > 0` 直接表示
「低头比期望快、需要抬头」，与舵面正方向一致，输出端不用再取反。
注意 `RATE_GAIN` 与 `MAX_RATE` 影响很小——pitch 低于 23° 时角度差最大只有 15°，
`rate_cmd` 远达不到 ±35 限幅，真正决定力度的是 `RATE_KD`。

阶段 1 只以「pitch 跌破目标角」作为退出条件，不加角速率或绝对角度判据。
11.12 两发曾因 5 帧滑窗在起飞首帧误触发、导致整个上升段 pitch 输出为 0，故回退到最简形式。

不能用绝对角度：发射角本身就在 38~43°，写死 40° 会在起飞瞬间立即触发。
11.11 实测 21 发的模拟结果：多数发次在 30.0~31.5° 停止；低头慢的 20~27 在 36~40° 停止（原峰值 48~70°）；14 发在 33.1° 停止（原 51.8°）；10 发全程低于 30°，不触发，正常转入阶段 2。若抬头阶段始终到不了停止角，输出会保持 `PULL_US` 直到下降段判据触发——方向是抬头，不会发散，但会持续打舵。

**roll**：自稳目标由 `DART_ROLL_HOLD_DEG` 固定为 **0°（机翼水平）**，不再沿用起飞瞬间的横滚角——原逻辑会把发射架上的初始倾斜带入整段飞行。`DART_ASCENT_ROLL_COMPENSATION_ENABLE` 现在只决定是否在上升段插入固定抬升，默认 0 即全程走 `calculate_roll_hold()` 的 PID 自稳。

三条轴的输出经 `write_servo_outputs()` 混控后写入 TIM2。

### 5.7 视觉滤波

`update_vision_filter()` 每次控制周期执行，两种模式由 `DART_VISION_FILTER_MODE` 选择，**默认 `DART_VISION_FILTER_RAW_RATE`**。

数据入口：USART1 中断解析出 8 字节帧后写入无锁 mailbox（`x`、`y`、`recognized`、`tick_ms`、递增 `sequence`）。控制任务用两次读 `sequence` 的方式取一致快照。

测量有效性：`recognized = 1` 且 `|dx| ≤ 160`、`|dy| ≤ 120`。

**RAW_RATE 模式**：

- 位置角直接取当前帧 `atan((pixel - 0) / focal)`，不做低通。
- 角速率由相邻有效帧差分得到；首帧、重新捕获首帧、无目标帧一律置 0。
- 帧间隔合法范围 5–100 ms；速率经一阶低通（`RC = 20 ms`），并限幅 ±360 °/s。
- 位置不做滤波，因此不存在 EKF 的预测滞后。

**EKF 模式**（可切回，代码保留）：

- 状态 `[视线角, 视线角速率]`，匀角速度模型，过程噪声 5.0、量测噪声 9.0 px²。
- 量测模型 `pixel = center + focal × tan(angle)`，雅可比 `focal × (1 + tan²)`。
- 两轴创新量都必须落在 ±180 px 内才接受整帧，否则整帧丢弃。

两种模式共用后续逻辑：

| 判据 | 行为 |
|---|---|
| 250 ms 内无新帧 | `link_valid = 0` |
| 120 ms 内有过目标 | `valid = 1`（可使用） |
| 超过 500 ms 无目标 | 复位两轴滤波器，`valid = 0` |
| 启动后 1 s 仍无链路 | 起飞前置 `VISION_ERROR`，LED 闪白 |

### 5.8 下降段引导

`run_descent_guidance()` 流程：

1. roll 仍按起飞 roll 保持（补偿开启时按补偿目标），写入遥测。
> **当前 `DART_YAW_ABS_LOCK_ENABLE = 0`，本节描述的锁定逻辑未编译进固件。**
> 关闭时 `update_yaw_best_lock()` 是空操作，`yaw_unlock_output()` 直接回退到
> `calculate_yaw_hold()`（保持发射航向），遥测 `output_yaw_deg` 也报发射航向。
> 下面保留设计说明，需要时把开关置 1 即可恢复。

2. **每周期更新「最佳航向」**（`update_yaw_best_lock`）：只做一件事——
   `|los_yaw_deg|` 创新低时，把**当前 `ins->Yaw`** 记进 `yaw_best_deg`。
   视线角越接近 0 说明目标越靠近画面中心，此刻的机头朝向就是目标方位。
   目标丢失后本函数不再被更新，最佳航向自然冻结，不需要额外的"锁存触发"逻辑。
3. 目标无效时（**连续丢失视觉帧达到 `DART_DESCENT_UNLOCK_LOST_FRAMES = 2` 帧**，约 77 ms；
   或链路中断导致 `vision.valid` 掉 0）：
   - **yaw**：`yaw_unlock_output()`。最佳航向有效则用 `yaw_vision_pid` 对
     `wrap_180(yaw_best_deg − ins->Yaw)` 做闭环；从未识别到目标则回退到 `calculate_yaw_hold()`
     （保持发射航向）。用的是**与视觉分支同一个 PID 和同一个输出符号**，保证输出连续、不跳变。
   - **pitch**：滑翔速率环拉向 `DART_GLIDE_PITCH_DEG`（见下节）。
   - `output_yaw_deg` 上报最佳航向，地面可直接看出"目标指向哪里"。

> **为什么只记 yaw、不记 `yaw ± 视线角`**：加减视线角会引入符号歧义——相机坐标与 IMU 偏航
> 是否同向，从闭环遥测里根本测不出来（`corr(舵面, Δyaw)` 中位 −0.01，闭环把两者解耦了）。
> 而"目标居中时的机头朝向"只用 `ins->Yaw` 一个量，**与视线角的符号完全无关**，天然免疫这个问题。
>
> 更新判据带 `DART_YAW_BEST_MARGIN_DEG = 0.15°` 的改进量要求：视线角必须比历史最优再小 0.15°
> 才更新，避免单帧噪声把锁定角钉在错误位置。

11.12 实测回放（取 `argmin |视线角|` 处的 yaw）：

| 文件 | 最佳 yaw | 脱锁时 yaw | 发射 yaw | 最佳−脱锁 |
|---|---:|---:|---:|---:|
| 15 | −48.32 | −50.85 | −49.73 | +2.53 |
| 08 | −40.94 | −32.38 | −42.34 | **−8.56** |
| 17 | −17.24 | −9.52 | −17.55 | **−7.72** |
| 05 | −44.41 | −43.24 | −44.19 | −1.17 |

「最佳−脱锁」普遍为负，说明脱锁时机头已经越过了目标方位 1~8°，锁定后会把这段偏差拉回来；
而「最佳−发射」多在 ±3° 内，说明目标本来就在发射方向附近，这个功能修正的是**几度量级的偏差**，
不是几十度的大转弯。

4. 目标有效时，首次进入复位两个视觉 PID，然后计算：

```text
camera_yaw_rate   = sign × (视觉 x 角速率 + 机体 yaw 角速率)
camera_pitch_rate = sign × (视觉 y 角速率 - 机体 pitch 角速率)
yaw_command       = LOS_yaw   + T_d × camera_yaw_rate
pitch_command     = LOS_pitch + T_d × camera_pitch_rate
（角速率限幅 ±15 °/s，指令限幅 ±10°；前视项再单独限幅 ±3.0°）
```

5. 按当前 roll 把相机平面指令旋转到机体轴：

```text
yaw_body   =  cos(roll) × yaw_camera   + sin(roll) × pitch_camera
pitch_body = -sin(roll) × yaw_camera   + cos(roll) × pitch_camera
```

6. 单轴模式：`DART_MODE_PITCH` 时 yaw 指令与输出置 0 并复位 yaw 视觉 PID；`DART_MODE_YAW` 时对 pitch 做同样处理。
7. 目标角写入遥测 `target_*` 与 `output_*`；pitch 上报值取 `-pitch_command`（下降段方向修正）。
8. 输出：`yaw_output = -1 × 视觉 PID(yaw_command)`；`pitch_output` 走滑翔速率环，目标角取 `当前角 - pitch_command`（见下节）；roll 保持，混控写舵机。

这里不是完整经典比例导引：没有距离、速度与闭合速度，只有视线角与惯性系视线角速率前视项（前视追踪，lead pursuit）。

#### 滑翔速率环（`DART_DESCENT_GLIDE_ENABLE`）

下降段默认让机头跟随目标一路低头：11.11 实测 21 发，pitch 从 0° 掉到 −55°（中位），角速率 −80 °/s，
目标在画面里只停留约 280 ms。目标是让机头**缓慢**收敛到 −30° 附近，识别时 gyro ≈ 0。

这里不按角度误差直接给力，而是**先给一个期望低头速率，再对速率做闭环**：

```
期望速率 = GAIN × (当前角 − 目标角)        // 限幅 ±MAX_RATE
实际速率 = −DART_INS_PITCH_RATE_RAD_S × RAD_TO_DEG   // 低头为正
舵面     = SIGN × RATE_KD × (期望速率 − 实际速率)
```

为什么绕一层速率环：直接按角度误差给力，误差大时舵面就打满，机头被推着冲过目标角再拉回来，
形成「掉得快 → 过冲 → 反弹」。速率环把误差翻译成"每秒转多少度"，接近目标时期望速率自动减小，
到达时速率归零，天然不过冲；同时速率误差项本身就是阻尼项。

**两段共用同一个速率环，但增益和限幅各自独立**（2026-11-15 拆分）：
视觉段要比滑翔段更激进（有目标就快速压过去），滑翔段也不能太慢。
共用一个 GAIN 时是跷跷板——为了视觉跟得快把 GAIN 调大，滑翔段就会过驱到舵面反转（见下）。

| 参数 | 滑翔段 | 视觉段 | 作用 |
|---|---:|---:|---|
| 角度→速率增益 | `DART_GLIDE_RATE_GAIN` 5.0 /s | `DART_VISION_PITCH_RATE_GAIN` **5.0 /s** | 时间常数均为约 0.20 s |
| 速率限幅 | `DART_GLIDE_MAX_RATE` 80 °/s | `DART_VISION_PITCH_MAX_RATE` 100 °/s | 误差大时的上限 |
| 速率环增益 | `DART_GLIDE_RATE_KD` 2.5 us/(°/s) | 同左 | 两段共用 |
| 输出限幅（低头/抬头） | −150 / +250 us | 同左 | 见下方"力矩反转" |

`DART_GLIDE_PITCH_DEG` = **−45°**（基准滑翔角，11.15 起由 −35° 加深）。

**输出限幅为什么非对称**：11.14 实测俯仰通道超过约 **−17°** 后力矩反转——00012 推到 −22.1°，
机头反而从 −20° 抬到 −17°，卡住下不去。低头侧限到 150 us（13.5°）留 3° 余量；
抬头侧刹车本来就要靠大偏度，实测 +24°（00005）仍正常，只防极端值，放到 250 us（22.5°）。

按 00012/13/14 实测数据回放（GAIN 5.0/8.0 + 上述限幅）：

| 架次 | 段 | 旧舵面最低 | 新舵面最低 | 低头打满帧 |
|---|---|---:|---:|---:|
| 00012 | 滑翔 | −22.1° | **−13.5°**（限幅）| 21 / 39 |
| 00014 | 滑翔 | −18.4° | **−13.5°**（限幅）| 8 / 25 |
| 00013 | 视觉 | −2.8° | −5.0° | 0 |

舵面被压在 −13.5°，**再也不会进入 −17° 的反转区**；代价是滑翔段约一半的帧顶在限幅上，
没有额外余量。

**视觉追踪期间的接法**：`目标角 = 当前角 − pitch_command`，展开后
`期望速率 = GAIN × pitch_command`（当前角被消掉），所以视觉分支本质是**速率指令**，
滑翔角 −45° 并不参与。`cmd = 10°` 时视觉段要求 80 °/s（限幅 100 未触发），约 0.125 s 走完 10°。

> 注意：视觉指令本身经常很小（00013 均值 +0.2°、00014 均值 −0.6°），因为目标基本在轴线上，
> 纯追踪的指令就是"别低头"。所以视觉段 82~100% 的帧舵面在抬头刹车，这是纯追踪的固有特性，
> 不是增益不够。

> **符号（已用实测数据锁定）**：`pitch_command > 0` 表示目标在视线下方、需要低头。
> 依据是 11.12 全部 28 发下降段 `corr(los_pitch, out_pitch) = −0.84`（无一例外为负），
> 即旧代码的 `out = −KP·cmd`；且 `corr(los_pitch, Δpitch) < 0`，说明该符号确实闭合了回路。
> 早期版本写成 `当前角 + pitch_command`，等效于把视觉指令反接，已修正为减号。

目标丢失/链路中断时，滑翔环按基准角 −30° 单独工作，yaw 回自稳保持发射航向。

实测依据：28 发 pitch 速率只有 −30 °/s 时，目标停留 **713 ms**，是其他发次（−80 °/s、280 ms）的 2.5 倍。
拟合关系 `los 速率 ≈ 1.21 × pitch 速率`，pitch 每慢 1 °/s，目标就多留 1.2 °/s。

#### 落地检测（`DART_LANDING_DETECT_ENABLE`）

下降段三轴合成角速率突增：

```text
|ω|² = gx² + gy² + gz²                （rad/s）
|ω| > 500 °/s                          → 立即判定落地
|ω| > 400 °/s 且上一周期也 > 400 °/s    → 判定落地（覆盖软着陆）
```

11.11 实测 21 发：飞行中最大 497 °/s，落地帧 510~3326 °/s（跳变 10~149 倍）。
单帧 >500 判据 **21/21 完全命中、零误触发**；>400 连两帧用于兜底（28 发软着陆仅 510）。
落地后只置 `DartControl.landed` 标志，不改变控制输出。

### 5.9 PID

通用实现在 `controller.c`，控制任务通过 `calculate_axis_pid()` 调用：

```c
rate_deg_s = rate_rad_s × RAD_TO_DEG;
PID_Calculate(pid, rate_deg_s, rate_deg_s + error);   // Ref - Measure == error
```

因此角度误差仍进入比例与积分，而微分由钩子函数 `gyro_rate_derivative()` 直接给出 `Dout = -Kd × 角速度`，不再对误差求导（`OLS_ORDER = 0`）。

| 机制 | 行为 |
|---|---|
| 输出限幅 | ±420 µs |
| 积分限幅 | ±120 µs |
| 死区 | 0.20°；死区内 `Output = Iout + Dout`，保留积分与角速度阻尼 |
| 积分分离参数 | 全局 `A = 10`、`B = 2`；**`ChangingIntegrationRate` 原本未启用**（所以这两个数一直是死参数）。2026-11-18 起只给视觉 yaw 打开，用独立的一组 10/10 |
| 输出 / 微分低通 | RC 均为 0.01 |
| dt 来源 | DWT 实测；`dt <= 0` 或 `> 20 ms` 回退 2 ms |
| 复位时机 | 起飞确认、进入下降段、视觉激活/退出、状态切换 |

两套参数：自稳（yaw 5.0/0.01/0.5、pitch 10.0/0.05/0.5）与视觉（yaw 5.0/0.1/0.5、pitch 10.0/0.1/5.0），roll 固定 10.0/0.01/1.0。视觉 Kd 的量纲是 µs/(°/s)，符号需在机架上确认。

### 5.10 混控与舵机输出

```c
pitch *= DART_PITCH_OUTPUT_SIGN;   // +1
yaw   *= DART_YAW_OUTPUT_SIGN;     // -1
roll  *= DART_ROLL_OUTPUT_SIGN;    // -1

m0 =  pitch + yaw + roll
m1 =  pitch - yaw + roll
m2 = -pitch - yaw + roll
m3 = -pitch + yaw + roll
```

每个通道依次：限幅到 `±(2550-1550) µs` 与 `±(1550-550) µs` → 加中位 1550 µs → 与上一周期比较，单周期变化不超过 30 µs → 写 TIM2 比较寄存器。

PID 输出是相对舵机中位的偏置，不是绝对 PWM 值。步进限制会掩盖瞬态方向错误，验证舵面时应观察完整行程。

### 5.11 遥测发送

`attitude_telemetry_send()` 在 `LED_Task` 中每 20 ms 调用：

- 未 armed 或 IMU 未就绪直接返回；`huart1` 忙时跳过本帧。
- 关中断复制姿态、陀螺与输出角（约数十字节），保证同一帧数据一致。
- 角度 ×100、角速度 ×10 转 int16 大端填充，LOS 增量、四路舵机角、加速度/指令/PN 角速率/yaw 输出一并打包，计算 CRC8，`HAL_UART_Transmit_IT` 发送 45 字节。
- 使用静态发送缓冲，因此依赖 `gState` 判断上一帧是否完成。

### 5.12 LED

| 状态 | 颜色 | 引脚电平（低有效） |
|---|---|---|
| `READY` | 蓝 | R0 G0 B1 |
| `IMU_READY` | 绿 | R0 G1 B0 |
| `SERVO_READY` | 青 | R0 G1 B1 |
| `LAUNCHED` | 红 | R1 G0 B0 |
| `ASCENT` | 黄 | R1 G1 B0 |
| `DESCENT` | 紫 | R1 G0 B1 |
| `VISION_ERROR` | 白闪 | 200 ms 翻转 |

`VISION_ERROR` 只覆盖对外显示，不改变 `DartControl.flight_state`；起飞后不再显示，视觉失联由下降段目标丢失逻辑处理。

### 5.13 并发与中断

- `INS` 由 IMU 任务每 1 ms 更新，控制任务用关中断 `memcpy` 取快照。
- 视觉 mailbox 用递增 `sequence` 实现单生产者/单消费者无锁读：读前读后序号一致才采用。
- USART1 使用单字节中断接收，每字节一次 IRQ；115200 下满速约 11 520 IRQ/s。协议靠 SOF/EOF/CRC 与逐字节滑窗重新同步。
- ORE 等错误在 `control_uart_error_callback()` 中清标志并重启接收，帧索引清零。
- USART1 中断优先级 5 等于 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`；回调中若需 RTOS API 只能用 `FromISR` 版本，且不要做耗时操作。

## 6. OpenMV 视觉端

### 6.1 启动与握手

`main.py` 顶层依次执行：`=== BOOT ===` → `UART(3, 115200, read_buf_len=2048)` → 传感器初始化 → `wait_for_handshake()` → 主循环。

`wait_for_handshake()`：

1. 连发 3 次复位帧 `5B 5B 5B CRC`，每次间隔 5 ms，清空接收缓冲。
2. 逐字节搜索 `A5`，校验 EOF 与 CRC，MODE 必须 ≤ 3。
3. 收到合法帧后回 3 次 `5A MODE FE CRC`，间隔 2 ms，再次清空缓冲并返回 mode。

因此 **不接 F103 时脚本不会进入主循环**，会每秒打印 `still waiting, buf_len = N`。

### 6.2 图像与目标检测

| 项目 | 值 |
|---|---|
| 帧尺寸 / 格式 | QVGA 320×240，RGB565 |
| 传感器读出窗口 | `(0, 700, 640, 480)` |
| 检测 ROI | `(0, 0, 320, 240)`，随目标动态收缩 |
| 制导中心 | `(160, 120)`，ROI 中心 |
| 绿色阈值 | L 9–100，A −102–−25，B 0–127 |
| 曝光 / 增益 | 固定 800 µs / 20 dB，白平衡关闭 |
| 启动跳帧 | 1500 ms |

检测流程：`find_blobs()` 在 `cur_roi` 内找色块 → 取面积最大者 → 以 `blob.rect` 更新跟踪 ROI（外扩 40 px 并裁剪到画面内）→ 未识别时 ROI 复位为全画面 → 3 帧时间中值滤波抑制跳点 → 计算 `dx = cx - 160`、`dy = cy - 120`。

单轴模式下：MODE_PITCH 时 `dx = 0`，MODE_YAW 时 `dy = 0`。

### 6.3 上行发送

`send_target(dx, dy)` 与 `send_no_target()` 都先检查 `uart.txdone()`，忙则丢帧；帧内偏移为有符号 16 位大端，CRC8 覆盖前 7 字节。写串口耗时超过 20 ms 会打印 `[DEBUG] write slow` 并累加 `TX_SLOW_COUNT`。

### 6.4 遥测解析与屏幕

`poll_telemetry()` 每次主循环调用：

- 读空串口缓冲，追加到 `telem_buf`，按 45 字节切帧，校验 EOF 与 CRC。
- 有效帧更新陀螺、姿态、输出角、LOS 增量、四路舵机角、mode、state、flags，并锁存飞行状态：状态落在 3..5 即 `flight_seen = True`；首次收到 5 记录 `descent_seen_ms`。
- `telem_frames` 累加，帧数超过 200 字节缓冲时清空并打印 `telem_buf overflow`。
- 300 ms 无有效帧则 `telem_link = 0`。

屏幕叠加（左上角逐行）：

```text
FPS:<fps>
t=<ms> T:<有效遥测帧数>
P:<pitch> Y:<yaw> R:<roll>      无链路时显示 --
GX:<gx> GY:<gy> GZ:<gz>
OP:<out_pitch> OY:<out_yaw> OR:<out_roll>   flags bit4 无效时显示 --
M:<mode> S:<state> L:<link> V:<目标有效>
<录像文件名>                      仅录像时
```

识别到目标时额外画红框与 `Found! X=.. Y=..`，并画蓝色跟踪 ROI 矩形。

`OVERLAY_LEVEL = 1`（当前配置）为精简模式，只显示三行：

```text
P:<pitch> Y:<yaw> R:<roll>
OP:<out_pitch> OY:<out_yaw>
M:<mode> S:<state> <fps>fps[ E<录像同步失败数>/<日志flush失败数>]
```

`E` 字段只在 SD 同步失败次数不为 0 时出现（见 6.5「SD 同步失败」），正常录制时看不到。

帧率是刻意画进叠加层的：叠加层会被烧进录像帧，所以录完直接看视频就能知道
当时的实际主循环帧率，不需要另外接串口读。改录像格式、改抽帧间隔后，
用这个方法可以直接验证收益。
状态字母：`R` READY、`I` IMU_READY、`S` SERVO_READY、`L` LAUNCHED、`A` ASCENT、
`D` DESCENT、`E` VISION_ERROR、`G` DEBUG、`N` LANDED。

### 6.5 录像

- 默认走 **MJPEG 直编码**（`mjpeg.Mjpeg(path)` + 逐帧 `write(img, quality=60)`），
  文件为 `rec_00001.mjpeg`，**拷到电脑即可用 VLC / 剪映直接播放，不需要导出**。
- **写入失败自动降级**：`mjpeg.Mjpeg.write()` 连第一帧都抛异常时，删掉只剩文件头的残片，
  置 `record_fallback_bin = True`，改用 `image.ImageIO` 重新开一段 `.bin`。
  之后整个运行周期都不再尝试 mjpeg。这样即使某块板子的 mjpeg 模块不可用，也还能拿到画面。

  **`Compression Failed!` 是 `fb_alloc` 帧缓冲池不够，不是 MicroPython 堆。**
  OpenMV 的 JPEG 编码器从 `fb_alloc` 申请输出缓冲区，与 `gc` 管理的是两套内存。
  细节和定位方法见 **6.5.1**。

  对应的三层处理：

  | 时机 | 动作 |
  |---|---|
  | 写之前 | `gc.mem_free() < JPEG_MIN_FREE_BYTES`（28 KB）→ 强制回收一次（只防 Python 侧 OOM，**对 `fb_alloc` 无效**）|
  | 写失败 | `gc.collect()` 后重试一次 |
  | 重试仍失败 | 降级到 `ImageIO` 写 `.bin`，写间隔自动放宽到 `RECORD_INTERVAL_BIN_MS`（100 ms，10 fps）|

  `.bin` 单帧 150 KB，按 21 fps 写要 3.1 MB/s 会把主循环拖死，所以降级后自动降到 10 fps
  （约 1.5 MB/s）。画面会卡，但至少拿得到。

**实测帧率只有约 8 fps，不是 30 fps。** 11.15 六发：每发 15~18 帧，覆盖 0.12~2.39 s
（用叠加层的 `P/Y/R` 和遥测逐帧对齐确认），即 **2.27 s / 18 帧 ≈ 7.9 fps**。
`RECORD_INTERVAL_MS = 33`（30 fps）根本没跑到——真正的瓶颈是单次 `write()` 约 125 ms
（17.5 KB/帧，约 140 KB/s），受 SD 卡写入速度限制。

同时 **AVI 头里的帧率写错了**：`rec_00003` 头里是 13.8 fps，实际 7.9 fps，
所以用播放器看会**偏快约 1.7 倍**。做时间对齐分析时不能信播放器的时长，要按帧号对应遥测。

#### 6.5.2 `record_err.txt` 实测：mjpeg 只有 9% 成功（2026-11-15 下午）

一次完整的日志（22 段录像）终于把这件事定量了：

| 结果 | 段数 | 表现 |
|---|---:|---|
| mjpeg 成功 | **2** | 00022（62 帧）、00027（47 帧），全程无报错，约 20 fps |
| 第一帧就失败 | **12** | `frames=0 reason=write_fail`，然后降级 `.bin` |
| 写了几帧后失败 | **8** | `frames=4~8`，中途 `Compression Failed!` |

失败的那 20 段全部落到 `.bin`（13~20 帧、约 5~8 fps），**数据没丢，但不可直接播放**。

典型日志：

```text
19603,start,/sdcard/rec_00006.mjpeg fmt=mjpeg
19618,write,Compression Failed!          ← start 之后 15 ms
19623,stop,rec_00006.mjpeg frames=0 reason=write_fail
19664,start,/sdcard/rec_00006.bin fmt=bin
22283,stop,rec_00006.bin frames=20 reason=should_stop
```

**关键点：`gc.collect()` 后的重试也失败了**（没有 `retry` 行），
说明不是 Python 堆的问题，就是 `fb_alloc` 不够。而且成功/失败在时间上随机
（00027 在同一轮开机里成功、前一段 00026 失败），说明**余量正好卡在边界上**。

**内存账**（QVGA RGB565）：

```text
帧缓冲            320 x 240 x 2 = 150 KB
JPEG 编码 scratch  约 150 KB（OpenMV 按整幅申请）
------------------------------------------
合计              约 300 KB
```

**对策：录像前 `img.mean_pool(2,2)` 降到 160x120。** scratch 从 150 KB 降到约 38 KB，
总量从 300 KB 降到 190 KB，余量拉开 4 倍。代码里是 `RECORD_POOL_DIV`：

| `RECORD_POOL_DIV` | 录像分辨率 | 编码 scratch | 可靠性 |
|---:|---|---|---|
| 1 | 320×240 | 约 150 KB | **实测 9%** |
| **2（默认）** | **160×120** | **约 38 KB** | 余量 4 倍 |

代价是叠加层文字在 160×120 下会糊——遥测 CSV 里有完整数据，不影响事后分析。
另外补了 `sensor.set_framebuffers(1)`，明确只占一个帧缓冲。

> 池化只在 mjpeg 路径做。`.bin` 走原始帧，池化只会把 150 KB 的帧缩成 38 KB 丢分辨率，
> 换不来任何好处——它是写卡瓶颈，不是编码瓶颈。

#### 6.5.3 为什么「地面手动测试录像都成功，一飞行就不行」（2026-11-16 补充）

11.15 的 `telem_00022` 是一次**地面手动测试**（`state` 只出现 3→4，3.0 s，没有下降段也没有落地），
它的录像 `rec_00022.mjpeg` 是当天最完整的一段：**62 帧 / 3.0 s = 20.7 fps，5.9 KB/帧**。

这个数字和 `main.py` 顶部记录的台架实测**完全吻合**（MJPEG q=60 写卡 4.6 ms/帧，
加 snapshot 25.4 + find_blobs/叠加/串口 17.9 = 47.8 ms → 20.9 fps）。

**所以地面测试确实「没问题」。问题在于地面测试测的不是飞行时的负载。**

把 11.15 全部 36 个能解析的录像按帧大小分组：

| 组 | 文件数 | 均帧大小 | 帧率 | 帧数 |
|---|---:|---:|---:|---:|
| QVGA 飞行（00001~00027） | 27 | **14.6 KB** | **4.4~7.3 fps** | 9~20 |
| QVGA 地面（00022） | 1 | **5.9 KB** | **20.7 fps** | 62 |
| 160×120 飞行（00028~00039） | 12 | **5.4 KB** | **16~20 fps** | 38~52 |

**帧率几乎完全由「压缩后一帧多少字节」决定，不是由分辨率、也不是由内存决定。**

| 架次 | 场景 | KB/帧 | fps | 单帧耗时 | 扣除固定 43 ms 后的写卡 |
|---|---|---:|---:|---:|---:|
| 00022 | 地面静态 | 5.9 | 20.7 | 48 ms | **5 ms** |
| 00027 | 飞行（画面较干净） | 8.0 | 19.2 | 52 ms | 9 ms |
| 00003 | 飞行（天空+地面+树） | 16.9 | 7.2 | 139 ms | ~96 ms |
| 00039 | 飞行（池化 160×120） | 5.6 | 16.1 | 62 ms | 19 ms |

**飞行画面的 JPEG 帧是地面的 2.5 倍大**（14.6 vs 5.9 KB），写卡时间从 5 ms 涨到 96 ms。
主循环被拖到 5~7 fps，同时编码器申请缓冲区也更容易失败，于是抛 `Compression Failed!`
并降级 `.bin`。**两个现象是同一个变量的两个后果：帧大小。**

**为什么地面测试验证不了：**

1. 画面静态 → 帧小 2.5 倍 → 带宽和编码器负载都落在安全区；
2. 地面不会经历「高速 + 落地」时的剧烈画面变化（运动模糊、天地线扫过、树影）；
3. 地面测试通常只跑 3 s，样本太少，碰不到边界。

**判据**：看「平均帧大小」这一个数就够了。

| 均帧大小 | 风险 |
|---|---|
| < 8 KB | 安全（实测 16~20 fps） |
| 8~12 KB | 边缘（00027 是 8.0 KB / 19 fps，00015 是 11.6 KB / 5.4 fps） |
| **> 12 KB** | **必出问题**（QVGA 飞行全部落在这里） |

**对策（已实施并验证）**：`RECORD_POOL_DIV = 2`，录像前 `mean_pool(2,2)` 降到 160×120。
00028~00039 十二发全部 16~20 fps、38~52 帧，**没有一次失败**。

**如果要回到 QVGA**：带宽上限就摆在那里，QVGA 一帧 15~20 KB，
按实测 5~7 ms/KB 算，单帧写卡 75~140 ms，**理论上限就是 5~7 fps**，不可能到 20 fps。
想让 QVGA 也快，只能降 `RECORD_JPEG_QUALITY`（60 → 30~40，帧大约减半 → 10~12 fps），
或者接受 5~7 fps。

**一个还没闭合的点**：同样是 5.6~5.9 KB 的帧，地面 00022 只要 5 ms 写卡（0.9 ms/KB），
而 160×120 的 00039 要 19 ms（3.4 ms/KB）。帧大小相同、耗时差 3.8 倍，
说明除了字节数还有别的因素（SD 卡状态、编码器按像素计的工作量、`mean_pool` 本身的耗时）。
这不影响上面的结论，但「每 KB 成本」不是一个常数，别拿它做精确预测。

> 注意：写失败时 `update_recording()` 会 `os.remove()` 删掉残片再降级 `.bin`，
> 所以「目录里没有坏 `.mjpeg`」不等于「没失败过」——失败的那一段会被删掉。
> 要判断有没有失败，只能看 `record_err.txt` 里的 `reason=write_fail`。

#### 6.5.1 零帧录像怎么定位

**先分清两块内存。** `Compression Failed!` 缺的不是 `gc` 管的那块：

| 内存池 | 管理者 | 装什么 | 不够时 |
|---|---|---|---|
| MicroPython 堆 | `gc` | Python 对象、`img`、`Mjpeg` 实例 | `MemoryError` |
| `fb_alloc` 帧缓冲池 | 栈式分配器 | 帧缓冲、JPEG 编码临时缓冲区、`draw_*` 临时空间 | **`Compression Failed!`** |

所以写前那句 `gc.mem_free() < JPEG_MIN_FREE_BYTES` 和失败后的 `gc.collect()` 重试，
**对 `Compression Failed!` 基本无效**——它们看不到 `fb_alloc`。
留着只是顺带防 Python 侧真的 OOM。

**「与开机时长相关」这个说法已被推翻。** 遥测首行的 `t_ms` 就是 OpenMV 开机至今的毫秒数，
11.14 十发实测：

| 架次 | 开机时长 | 录像 |
|---|---:|---|
| 00002 | 15.9 s | ❌ 224 字节 |
| 00014 | 19.1 s | ✅ 344 KB |
| 00004 | 32.6 s | ❌ 224 字节 |
| 00003 | 43.2 s | ❌ 224 字节 |
| 00013 | 43.2 s | ✅ 358 KB |
| 00012 | 56.5 s | ✅ 283 KB |
| 00007 | 60.5 s | ❌ 224 字节 |
| 00001 | 86.6 s | ❌ 224 字节 |

同样 43.2 s 有成功也有失败，15.9 s 也失败过。**时长不是变量。**
而且 `t_ms` 不单调（00001 是 86.6 s、00002 只有 15.9 s），说明每发之前脚本都重跑过，
所以「落地标志没清」那条也解释不了这 7 发。

**224 字节 = AVI 头 + `LIST movi`，`dwTotalFrames = 0`，一个 JPEG 帧都没有。**
只可能是两种之一：

1. `start_recording()` 之后**第一帧都没写就被 `record_should_stop()` 掐掉**
2. **第一帧 `mjpeg.write()` 就抛异常**

这两种在文件上长得一模一样，11.14 当时没有日志，所以无法区分。

**现在能区分了**：`record_err.txt` 会记录完整的生命周期——

```text
<ticks>,start,/sdcard/rec_00001.mjpeg fmt=mjpeg
<ticks>,stop,rec_00001.mjpeg frames=0 reason=should_stop     ← 开完就停
<ticks>,write,Compression Failed!                            ← 第一帧写失败
<ticks>,stop,rec_00001.mjpeg frames=0 reason=write_fail
<ticks>,retry,rec_00001.mjpeg frame=1 ok                     ← 重试救回来了
```

`frames=N` 是实际写进去的帧数。**下次再出现 224 字节，直接看这个文件就能定性**，
不用再靠猜。

**现场两条对策（都保留）：**

1. **降级链路保底**：MJPEG 连第一帧都写不进去时，删残片、改 `ImageIO` 写 `.bin`，
   写间隔自动放宽到 100 ms。这是唯一能「保证不空手」的机制。
2. **降低编码缓冲需求**：`fb_alloc` 要同时装 QVGA RGB565 帧缓冲（150 KB）和
   JPEG 编码 scratch（约 150 KB），余量本来就紧。录像前先 `mean_pool(2,2)` 缩到 QQVGA
   再写，scratch 降到约 37 KB，能拉开 110 KB 余量（视频变 160×120）。

- **`GC_COLLECT_INTERVAL` 由 60 降到 20**：21 fps 下原来 2.9 秒才回收一次，太久；
  20 帧约 1 秒，单次 collect 十几毫秒，摊到每帧不到 1 ms。
- **错误写卡**：所有录像异常（open / write）都会追加到 `record_dir/record_err.txt`，
  格式 `ticks_ms,stage,异常文本`。现场没有串口时，飞完插卡看这个文件就能定位。
- 固件没有 `mjpeg` 模块时自动退回 `image.ImageIO(path, "w")` 原生流，文件为 `rec_00001.bin`，
  需要走 8.7 的导出流程。两种扩展名在编号时会同时检查，换格式不会撞号覆盖旧文件。
- 两种方式都是逐帧写，不在内存缓存整段视频。
- 触发：收到状态 3..5（起飞段）或状态 7（调试模式）的第一帧开始。台架调试没有发射，
  靠调试状态也能启动录像。
- 停止判据由 `record_should_stop(now, start)` 统一给出，录像与 CSV 共用：

  | 优先级 | 条件 | 停止时刻 |
  |---|---|---|
  | 1 | 收到落地标志（state=8），**且该标志晚于本次录像开始** | `landed_seen + LANDED_RECORD_TAIL_MS`（200 ms） |
  | 2 | 非 debug 且未检出落地 | `start + RECORD_MAX_FROM_LAUNCH_MS`（3000 ms） |
  | 3 | debug 且未检出落地 | 不设时间点，只等落地 |
  | 4 | 任何情况 | `start + MAX_RECORD_MS`（30000 ms）绝对上限 |

  落地标志优先于 3 s 兜底，所以正常飞行会在落地后 200 ms 就停，比原来的
  「下降 + 3 s」提前 30~40%。11.12 实测 16 发检出落地：进降→落地 846~1723 ms，
  平均可省 36%（中位 35%），最长一发（`telem_00032`）省 68%。

  **`landed_seen_ms` 必须晚于本次录像的 `start_ms` 才算数**：它是全局标志，
  落地后不会自动清零。若下一轮录像直接沿用旧时间戳，`record_should_stop` 会在
  第一帧之前就返回 True，文件只写出 `mjpeg.Mjpeg` 的索引帧（约 1 KB）就结束。
  现在两处兜底——起飞（状态 3..5）时清掉上一轮标志，`record_should_stop` 里再
  用 `ticks_diff(landed_seen, start) >= 0` 过滤旧值。
- 最小写间隔 `RECORD_INTERVAL_MS = 33` ms，即上限 30 fps。

**为什么改成 MJPEG**（2026-11-13 实测，OPENMV4 / STM32H743，QVGA RGB565，`tools/bench_encode.py`）：

两次实测取平均：

| 环节 | 耗时 | 单帧 |
|---|---:|---:|
| `sensor.snapshot()` | 25.4 ms | — |
| `ImageIO.write` 原始帧 | **25.2 ms** | 150.0 KB |
| `mjpeg.Mjpeg.write(q=50~60)` | **4.6 ms** | 5.6 KB |

存储环节快 **5.5 倍**，每帧省约 21 ms，数据量小 27 倍。

**真实帧率推算**（注意不能只看 snapshot+写卡）：改造前录像实测 14.6 fps，即总周期 68.5 ms，
减去 snapshot 25.4 与写卡 25.2，可得 `find_blobs` + 叠加绘制 + 串口收发合计约 **17.9 ms**。
这是与录像无关的固定开销。

| 方案 | 总周期 | 帧率 |
|---|---:|---:|
| 改造前（原始帧） | 25.4+25.2+17.9 = 68.5 ms | 14.6 fps（实测） |
| 改造后（MJPEG） | 25.4+4.6+17.9 = **47.8 ms** | **≈20.9 fps** |

所以预期提升是 **+43%**，不是单看存储环节得出的 33 fps——那个数字是**不含视觉的天花板**。
实际值看叠加层里烧进录像的 `xxfps`。

> 测 `img.compress(quality=Q)` 得到 0.0~0.2 ms，这是**惰性编码**的假象：`compress()` 只做标记，
> 真正编码发生在 `write()` 时。所以「纯编码耗时」只能从 `Mjpeg.write` 反推，不能单独测。

> **质量参数疑似不生效**：两次独立实测，q=50 / 60 / 75 都得到 5.6 KB/帧，差异小于 50 字节。
> 两种可能：一是台架场景（室内静态）细节太少，JPEG 早已饱和；二是 `Mjpeg.write` 的
> `quality` 关键字被忽略，实际用的是默认值。
> **影响有限**：无论哪种，5.6 KB 都远小于 150 KB，写入耗时也在 4.5~4.8 ms，结论不变。
> 质量到底如何，直接看录出来的视频判断，比继续测数字更实际。
> 飞行数据里由 `imageio_playback.py` 以 `EXPORT_QUALITY=60` 导出的平均是 7.4 KB/帧，
> 与台架同量级，说明默认质量本身是可用的。
- 每秒 `sync()`。**`sync()` 失败只计数、不中止录像**——它只是掉电时少丢数据的保险，
  写不进去才是致命的。见下节「SD 同步失败」。
  MJPEG 模式下若流对象没有 `sync()`，**不再退回 `os.sync()`**：单帧只有 5~8 KB，
  靠 `close()` 收尾即可，每秒全盘 sync 反而会阻塞几十毫秒。
- 存储占用：MJPEG 每帧 5~8 KB，4 s 飞行约 0.3 MB；原始流每帧 150 KB，同样 4 s 要 9 MB。
  后者跑几十发就能把卡写满，是提前结束的另一个来源。

#### SD 同步失败（2026-11-13 修正）

旧实现把 `sync()` / `flush()` 的异常和 `write()` 的异常放在同一个 `except` 里，一旦同步失败就
`stop_recording(); record_done = True`，**整段录像永久结束且不会重启**。实测 11.11/11.12 共 50 发：

| 现象 | 触发点 | 实测 |
|---|---|---|
| 录像停在约 1.0 s | 第 1 次 `sync()`（`RECORD_SYNC_MS = 1000`） | `rec_00018` 最后一帧 `P=-12.4 S:D`，而 CSV 已到 `pitch=-67.2` |
| CSV 停在约 2.0 s | 第 2 次 `flush()`（`TELEM_LOG_SYNC_MS = 1000`） | `telem_00018/20/33` 全在 2010~2030 ms 结束 |
| 正常收尾约 4.0 s | `descent_seen + 3000` | `telem_00015`：下降 1157 ms + 3000 = 4157，实际 4169 ms |

9/50 发录像被截断、约 18/50 发 CSV 被截断，且全部落在 1000 ms 的整数倍上。
文件尾部 EOI 完整，说明是程序主动 `close()`，不是掉电。

修正后：

- `write()` 失败仍然中止（会破坏 MJPEG 流，重试无意义）
- `sync()` / `flush()` 失败只累加 `record_sync_err` / `telem_log_sync_err`，下一周期再试
- 计数不为 0 时，叠加层状态行追加 `E录像次数/日志次数`，例如 `M:B S:D E1/2`

### 6.6 遥测 CSV

与录像并行，`telem_log` 在首次进入状态 3..5（或调试状态 7）时创建 `telem_00001.csv` 等文件，逐帧追加：

```text
t_ms,frame,mode,state,flags,gx_dps,gy_dps,gz_dps,
pitch_deg,yaw_deg,roll_deg,out_pitch_deg,out_yaw_deg,out_roll_deg,
los_yaw_deg,los_pitch_deg,s1_deg,s2_deg,s3_deg,s4_deg
```

停止条件与录像完全一致（共用 `record_should_stop`），每秒 `flush()` 一次。
**`flush()` 失败不再中止记录**，只累加 `telem_log_sync_err`（原因见 6.5「SD 同步失败」）；
只有 `write()` 本身失败才停止。视觉与串口始终不受影响。

### 6.7 回放与导出

`imageio_playback.py` 在 OpenMV 上独立运行（先停止 `main.py`）：

- 默认自动搜索 `/sdcard`、`/sd`、`/flash`、`/` 与当前目录，选择编号最大的 `rec_XXXXX.bin`。
- `STREAM_PATH` 指定文件时先校验存在；不存在则列出候选，不会误开别的文件。
- 使用 `csi.CSI()` + `ImageIO.read(copy_to_fb=True, loop=False, pause=True)` 按原始帧间时间播放。
- `EXPORT_MJPEG = True` 时在同目录生成同名 `.mjpeg`，已存在则拒绝覆盖，原 `.bin` 保留。
- 读到 `Frames played: N` 即结束；损坏文件会保留已读前缀并报告错误。

### 7.4.1 yaw 坐标系统一（2026-11-15）

本机 IMU 的 pitch/roll 互换且带负号（`DART_SWAP_INS_PITCH_ROLL = 1`），
INS 的 **yaw 轴整体与机体反向**：`yaw_ins = −ψ`、`gz = −ψ̇`。
相机是正向安装的（画面右 = 机体右），所以相机角度必须取反才能进入 INS 系。

11.14 录像 `rec_00013.mjpeg` 实测（相邻帧，目标方位变化可忽略）：

| 帧对 | Δyaw_ins | ΔX | ΔX/Δyaw_ins |
|---|---:|---:|---:|
| 25 → 26 | +0.5° | +9 px（+0.54°）| **+1.08** |
| 34 → 35 | +1.9° | +25 px（+1.50°）| **+0.79** |

正常相机应为 −1，实测 +1，确认 yaw 轴反向。

**历史问题**：`DART_CAMERA_YAW_SIGN` 原为 +1，靠 `DART_DESCENT_YAW_OUTPUT_SIGN = −1`
在输出端抵消。P 项被两个负号救回来，但 `−KD·gz` 在 INS 系下等于 `+KD·ψ̇`，
**变成正反馈**。表现为：小误差时舵面被角速率项压制（"反应慢"），
角速率一大就自己放大（00013 的 gz 从 10 涨到 200 °/s，e 折时间 0.135 s）。

**现在的约定**：所有进控制器的 yaw 量（`los_yaw_deg`、`camera_yaw_rate`、`gz`）
都在 INS 系，视觉 yaw 输出与 `calculate_yaw_hold` 结构完全一致，输出端没有任何
视觉专用符号。全系统只有 `DART_CAMERA_YAW_SIGN` 一处负责坐标系转换。

台架若发现 yaw 朝目标反方向转，只改 `DART_CAMERA_YAW_SIGN` 一个宏。

#### 7.5.4 视觉 yaw 五组参数的对比（11.15 的 00023~00027）

同一轮飞行里连改了五次 PID，用 `yCh = a·cmd + b·gz` 回归反推：

```text
a = -0.09·KP·k       k = f_true/f_code（焦距错几倍就乘几倍）
b = +0.09·KD·k
=> a/b = -KP/KD，与焦距无关；绝对值要除以 k 才是固件里的 KP/KD
```

| 架次 | 视觉帧 | KP/KD | gz RMS | gz 峰 | cmd RMS | \|cmd\|>5 | yaw 行程 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 00023 | 30 | 9.1 | 26.0 | 46 | 8.36 | 87% | 15.5° |
| 00024 | 32 | 8.2 | 32.0 | 54 | 6.99 | 56% | 14.3° |
| 00025 | 34 | 13.0 | 22.5 | 49 | 6.41 | 62% | 6.1° |
| **00026** | 32 | **12.2** | 29.4 | 46 | **5.31** | **34%** | 13.5° |
| 00027 | 41 | 19.6 | **42.6** | **82** | 5.65 | 41% | **22.4°** |

**结论一：五发都在摆，而且比 00015~00017 严重得多。**
那三发的 `gz` 峰值只有 20~30 °/s，这五发是 46~82 °/s。摆动周期约 0.5 s（2 Hz），
正好是 `1/(2×0.3)`——**这是 300 ms 环路延迟决定的极限环，不是单纯增益问题**。

**结论二：KP/KD 不能超过 ~15。**
00027 的比值 19.6（阻尼最弱），虽然 `cmd RMS` 不算差，但 `gz` 峰值 82 °/s、
yaw 行程 22.4°，是五发里最暴的。00023/00024 比值 8~9 但 KP 高，
`cmd RMS` 反而最差（8.36 / 6.99）——P 太硬，追着噪声跑。

**结论三：00026 那套（KP/KD ≈ 12，对应固件 20/2.0）是五发里最好的。**
`cmd RMS` 5.31、`|cmd|>5` 只占 34%，都优于其余四发。

**结论四：横滚耦合不是主因。**
`corr(dψ/dt, θ̇·sinφ/(cosθcosφ))` 在 −0.04 ~ −0.84 之间，但耦合项 RMS 只有 1.4~4.3 °/s，
而实测 `dψ/dt` RMS 是 17~50 °/s——耦合只占 10~25%。

**下一步不该再调增益，该降延迟：**

| 手段 | 省多少 | 位置 |
|---|---:|---|
| `MED_WIN` 5 → 3 | **约 50 ms**（群延迟 2 帧 → 1 帧） | `main.py`（2026-11-18 已改） |
| `DART_LEAD_TIME_S` 0.20 → 0.12 | 前视项本身在激励振荡 | `ctl_task.h` |

`MED_WIN=5` 在 20 fps 下是 250 ms 的历史窗口，群延迟约 2 帧（100 ms）。
已改为 **3 帧**：窗口 150 ms、群延迟约 50 ms，回路延迟 330 → 280 ms，
视觉 yaw 的 `G·T` 从 1.25 降到 1.06（边界 1.57）。代价是跳点抑制弱一点。

#### 7.5.5 末段「摆到中间又偏走」的成因（00034/00035）

两发都是同一个形态：中段确实把目标摆到轴线上了，然后目标快速扫出画面、丢目标转滑翔。

| 架次 | 下降起点 | 首次捕获 | 捕获时 relLOS | 最低 relLOS | 末段 relLOS 峰 | 剩余时间 |
|---|---:|---:|---:|---:|---:|---:|
| 00034 | 1.11 s | 1.32 s | 7.7° | **0.3°** | 17.2° | 1.12 s |
| 00035 | 1.21 s | 1.40 s | 0.2° | **0.5°** | 14.7° | 0.86 s |

**所以视觉和跟踪本身是work的**——中段 `relLOS` 最低到 0.3°/0.5°，机头确实对准了。

问题在末段：目标以 **38~58 °/s** 扫出画面。这个速率下，300 ms 环路延迟产生的稳态滞后是

```text
45 °/s × 0.3 s ≈ 13.5°
```

与实测的 14.7~17.2° 完全对得上。**不是「偏走了」，是滞后追不上。**

**而且指令被限幅卡住了。** `DART_LEAD_COMMAND_LIMIT_DEG` 还是 10——那是旧 18.9° 视场
（半视场 9.45°）留下的值，现在半视场是 18.45°。于是：

| 指令限幅 | P 项舵面 | 折算转向能力 | 追得上 38~58 °/s 吗 |
|---:|---:|---:|---|
| 10 | 18° | 约 36 °/s | **追不上** |
| **15（现）** | 27° | 约 54 °/s | 够用 |

00034 的 42 个视觉帧里有 **11 帧**顶在 ±10° 限幅上，全部在末段。放宽到 15° 后
仍在半视场 18.45° 以内，且中段正常跟踪（2~8°）完全不受影响。

**另外两个同样被卡住的环节**（这次没动，按需再放）：

| 参数 | 当前 | 目标值需要 | 说明 |
|---|---:|---:|---|
| `DART_LOS_RATE_LIMIT_DEG_S` | 15 | 38~58 | 视线角速率被压到 15，前视项算出来只有 3° |
| `DART_LEAD_MAX_DEG` | 3 | 8~12 | 与上式绑定（0.2×15=3） |

`DART_LEAD_TIME_S = 0.20` 的注释写的是「实测回路延迟约 50~80 ms」，但 7.5.1 的实测是
**200~300 ms**。也就是说前视时间本身是按错误的延迟定的，偏小 3 倍。真要放开，
建议先只动 `LOS_RATE_LIMIT` 和 `LEAD_MAX` 到 25 / 5，一次一档。

**末段 40~60 °/s 的扫出，本质是几何问题**：距离越近，同样的横向速度误差产生的方位角速度越大
（`dβ/dt ≈ V_横向 / R`）。00035 捕获时 relLOS 只有 0.2°——机头一开始就是对准的，
最后偏到 14.7°，而机头只转了 −5.2°，剩下 10° 全是平动造成的。这段靠调增益救不回来，
需要更早对准（发射架方向）或者更早捕获目标。

#### 7.6.1 焦距为什么会从 961 变成 480（2026-11-15）

`f_out = 1921 × 320 / W`，W 是传感器读出窗口宽度：

| `READOUT_ROI` | W | f_out | 视场 | 用 961 的后果 |
|---|---:|---:|---|---|
| (0, 700, 640, 480) | 640 | **961** | 18.9°×14.2° | 正确 |
| (0, 0, 1280, 960) | 1280 | **480** | 36.9°×28.1° | **上报角度只有真值的一半** |

11.15 起 `READOUT_ROI` 改成 `(0, 0, 1280, 960)` 之后，`IOCTL_SET_READOUT_WINDOW`
**真的生效了**（旧的 `(0, 700, 640, 480)` 一直没生效，所以 961 是对的）。
视场翻倍而 `DART_CAMERA_FOCAL_*_PX` 还是 961，导致：

- 上报的 `los_yaw_deg` / `los_pitch_deg` 只有真值的一半；
- 视觉环的等效增益减半（误差被缩小一半再进 PID）；
- 观感就是「**机头转过的角度是屏幕上显示的两倍**」，看起来像超调。

**两路独立实测**（11.15 的 00015~00017）：

| 方法 | 做法 | 结果 |
|---|---|---|
| 录像法 | `rec_00017` 取 6 个带 `Found! X=` 的帧，画面 X 对 yaw 回归 | 8.92 px/度 → **f = 511** |
| 遥测法 | 目标静止时 `d(相对LOS)/d(yaw) = f_true/f_code`；t=1.32→1.78 区间 | 斜率 −0.50 → **f = 480** |

遥测法在整段下降段回归会偏小（330~420），因为机头一直在朝目标飞、平动也在改变视线角；
所以取短区间或录像法更可靠。两者都落在 480~511，与 W=1280 的理论值 480 吻合。

**判据**：以后改 `READOUT_ROI` 必须同步改焦距，否则视觉环增益会整体错一个倍数。
改了之后用遥测法自查：任取一段有视觉的下降段，回归 `d(相对LOS)/d(yaw)`，
**斜率应该接近 −1**（目标静止、机体只转动时，视线角的变化量等于转角）。

#### 7.5.1 偏航回路的延迟与极限环（2026-11-15 实测）

11.15 六发数据里，yaw 在**上升段和下降段都在摆**，幅度 ±2~4°、周期约 0.5 s（约 2 Hz）。
不是下降段独有的问题。定量结果：

| 量 | 实测 | 说明 |
|---|---|---|
| 舵面 → 角速率延迟 | **198~264 ms**（6~8 个遥测帧） | `corr(yCh(t), gz(t+k))` 在 k=6~8 时最强，−0.61~−0.92 |
| 被控对象增益 | **2.2~3.9 °/s per °** | `dgz/dyCh`，上升段 3.5~3.9、下降段 2.2~2.8 |
| 回路增益 | **KP × 0.09 × 3.5 ≈ 6.3** | 角度误差 → 舵面 → 角速率 |
| 振荡频率 | **≈ 1/(2×0.21) = 2.4 Hz** | 纯延迟转满 180° 的频率，和实测 2 Hz 对得上 |

按一阶对象（τ=0.1 s）+ 纯延迟（0.21 s）扫参数，KD 从 1.5 提到 2.5：

| KD | 残余摆幅（K=2.2 / 3.5 / 3.9） | 外部扰动峰值 |
|---:|---|---:|
| 1.5 | 0.54 / **2.52** / 4.00 | 2.19 |
| **2.5** | 0.13 / **2.00** / 3.38 | 2.19 |
| 4.0 | 0.18 / 12.04 / 14.15 | 发散 |

**KD 4.0 以上会发散**，所以取 2.5 而不是更大。KD 只增加阻尼、不影响角度环增益，
对外部扰动的峰值偏差没有代价——这是它比降 KP 更划算的地方（降 KP 会把扰动偏差放大）。

#### 7.5.2 下降段航向为什么会「偏」（2026-11-15 实测）

滑翔帧（`outY` 等于发射航向的帧）里，yaw 相对发射航向的最大偏差：

| 架次 | 横滚均值 | 滑翔段 yaw 偏差 | 几何耦合 ∫c·dt |
|---|---:|---:|---:|
| 00001 | −0.8° | 3.9° | +0.4° |
| 00002 | +2.3° | 4.7° | −1.3° |
| **00003** | **+6.5°** | **3.7°** | **−3.4°** |
| 00004 | −0.5° | 9.0° | +0.5° |
| **00005** | **+4.4°** | **4.8°** | **−3.2°** |
| 00020 | −0.6° | 3.4° | +0.2° |

**横滚偏置会通过几何耦合变成航向漂移，而偏航陀螺看不到这一项：**

```text
psi_dot = (r + theta_dot * sin(phi)) / (cos(theta) * cos(phi))
```

其中 `r` 是陀螺测到的机体偏航角速度。滑翔角从 −35° 改到 **−45°** 之后，
`1/cos(theta)` 从 1.22 涨到 1.41，耦合项放大约 36%。

实测耦合速率 `c = theta_dot*sin(phi)/(cos(theta)*cos(phi))`：00003 峰值 **8.9 °/s**、
00005 峰值 **7.1 °/s**，其余四发只有 1.4~5.4 °/s——和横滚偏置完全对应。
按 `∫c·dt` 积分得到 −3.4° / −3.2°，与观测到的航向漂移同量级。

**横滚为什么会偏 4~6.5°**：`DART_ROLL_KI = 0`，纯 PD 对持续滚转力矩有稳态误差。
00003/00005 的横滚一直稳在 +6.5/+4.4 不收敛，说明存在约 65 µs 的等效常值滚转力矩
（KP=10 × 6.5° = 65 µs 正好抵消）。

**另外两处不是漂移、但看起来像「偏」：**

1. **2 Hz 极限环**（见 7.5.1），±2~4°，升降段都有。
2. **视觉 → 滑翔切换的目标跳变**：视觉把机头带走 3~8°，脱锁瞬间目标回到 `launch_yaw_deg`，
   误差阶跃。00004 最典型——t=2.08 视觉指令 +7.7°，t=2.10 脱锁目标 3.8°，误差 −6.1°，
   之后 0.3 s 才拉回来。

#### 7.5.3 视觉 yaw 为什么容易超调（2026-11-15 实测）

11.15 的 00015~00017 三发里视觉占下降段 45/37/42 帧，是第一次真正长时间闭环。
现象：**yaw 转过的角度比视觉指令峰值还大**。

| 架次 | 视觉帧 | yaw 行程 | 指令峰值 | 倍数 |
|---|---:|---:|---:|---:|
| 00016 | 32 | **7.3°** | 4.9° | **1.5×** |
| 00017 | 38 | **4.6°** | 2.4° | **1.9×** |
| 00015 | 45 | 7.0° | 6.7° | 1.0× |

而且摆动几乎不衰减（相邻两次摆幅比 0.5~1.2），典型的欠阻尼。

**根因是两段延迟叠加**：

```text
舵面 -> 角速率            约 200 ms（见 7.5.1，实测互相关）
相机曝光 + 中值滤波 + 串口  100~130 ms（MED_WIN=5，26 fps 下群延迟约 2 帧）
------------------------------------------
合计                      300 ms 以上
```

视觉指令是**相对角**（`yaw_command = LOS + 0.2×LOS_rate`，限幅 ±10°），
机头转过去之后 LOS 才会变小，而相机又要 0.1 s 才把新的 LOS 送回来。
这段时间里控制器一直按旧指令给舵，于是转过头。

**但真正的病根是焦距，不是增益。** 那时焦距还是 961（见 7.6.1），上报 LOS 只有真值一半：
P 项 `-0.09·KP·cmd` 被砍半，而 D 项 `+0.09·KD·gz` 作用在真实角速率上不受影响。
于是 `|D|/|P|` 达到 **0.79~0.94**，45/31/38 个视觉帧里有 **19/13/9 帧舵面被 D 顶反**
——这就是「输出看着反了」的来源。

焦距修正后 P 项自动翻倍，`D/P` 从 0.79~0.94 回到 **0.42**（KD=3.0）。
按「P 项本身大于 2° 却被 D 顶反」这个判据统计（114 帧）：

| KP/KD | 00015 | 00016 | 00017 | 合计 | D/P |
|---|---:|---:|---:|---:|---:|
| 20/3.5 | 10 | 1 | 2 | 13 | 0.49 |
| 20/3.0 | 9 | 0 | 1 | 10 | 0.42 |
| 20/2.5 | 5 | 0 | 0 | 5 | 0.35 |
| **20/2.0（现值）** | 3 | 0 | 0 | **3** | **0.28** |
| 20/1.5 | 0 | 0 | 0 | 0 | 0.21 |
| 18/5.0 | 13 | 9 | 4 | 26 | — |

**加大 KD 明显更差**——因为 D 本来就已经压过 P；KD 只往下调，不往上调。

**但 KD 不能无限降。** 它同时是阻尼项，按一阶对象 + 双段延迟模型，5° 阶跃的反向超调：

| KP/KD | 反向超调 | 收敛 |
|---|---:|---:|
| 20/3.0 | 2.46° | 0.51 s |
| **20/2.0** | **3.53°** | 0.51 s |
| 20/1.5 | 4.6° | 0.51 s |

也就是 **KD 越小越不会「看着反向」，但越容易冲过头**，两者直接对冲。
判据：实飞若出现摆振（`gz` 反复过零、yaw 峰峰值变大），把 KD 加回 2.5~3.0；
若只是「看着反向」而没有实际摆动，保持 2.0。真嫌跟踪慢，加 KP，别加 KD。

> 上升段视觉只占 6%（1008 帧里 61 帧），最近三发是 0 帧，所以这些结论主要针对下降段。
> 如果实飞还嫌摆，下一个旋钮是 `DART_LEAD_TIME_S`（0.20 s）——前视项在角速率大时会把
> 指令顶到 ±3° 限幅，指令回落时又会突然塌下来，本身就在激励超调。

KD 只能缓解，不能根治。

### 8.6 录像存储方案实测（`tools/bench_encode.py`）

换录像格式前必须先量一次，否则选型全靠猜。脚本在 OpenMV IDE 里直接运行，不需要 STM32，
会自动找 SD 卡、跑完清理临时文件。

测四组，全部**只算存储环节、不含 `sensor.snapshot()`**，所以可以直接横向比较：

| 编号 | 方案 | 关注点 |
|---|---|---|
| 1 | 只 `snapshot()` | 任何方案都要付的固定成本 |
| 2 | `image.ImageIO.write(img)` | 当前方案，150 KB/帧 |
| 3 | `img.compress(quality=Q)` | 纯编码开销，不写卡 |
| 4 | `mjpeg.Mjpeg.write(img, quality=Q)` | 方案 A：编码 + 写卡，可播 |
| 5 | `mean_pool(2,2)` + `ImageIO.write` | 方案 B：缩到 QQVGA 原始帧 |

判据：MJPEG 的存储耗时与第 2 组直接对比——更短就换；略长 5~15 ms 则同时把录制帧率
降到 10 fps 仍划算；长 15 ms 以上不划算，走方案 B 或直接降帧率。

`QUALITIES = (50, 60, 75)` 三档都测，因为 JPEG 编码耗时随质量变化通常不大，
但文件大小差得多，性价比最高的往往是较低质量。

### 8.6.1 主循环分段耗时（`tools/bench_stages.py`）

想加录像帧率时先跑这个，不要凭注释里那组旧数字改参数。它按**当前**配置
（`READOUT_ROI` 1280×960、`RECORD_POOL_DIV=2`、`OVERLAY_LEVEL=1`、质量 60）
逐段计时，并合成出「只优化这一段」时的 ms / fps：

| 段 | 说明 | 对应的旋钮 |
|---|---|---|
| 1 snapshot | 传感器固定成本，任何方案都要付 | 改 `READOUT_ROI`（会连带改焦距标定） |
| 2 find_blobs 全屏 y1 | 未锁定时扫全画面 | `y_stride=2`、收缩 `INIT_ROI` |
| 3 find_blobs 全屏 y2 | 同上，纵向隔行采样 | 精度代价 2 px ≈ 0.24°（f=480） |
| 4 find_blobs 锁定 ROI | 锁定后只扫目标 ±40 px | 自动生效 |
| 5 overlay(L1) | 框 + FPS + 状态行 | `OVERLAY_LEVEL` |
| 6 编码+写卡 | `mjpeg.write(quality=60)` | `RECORD_JPEG_QUALITY`、`RECORD_POOL_DIV` |

判据：**哪一段最大就先动哪一段**。当前实测约 20.8 fps，而 `RECORD_INTERVAL_MS=33`
（30 fps 上限）在主循环 48 ms 时是空转的——录像帧率 = 主循环帧率，不是间隔决定的。

## 9. 已知问题与风险

### 9.1 RAM 余量小（中高）

最近一次链接结果 `RW_IRAM1 = 19152 / 20480 B`，只剩 **1328 B**。这已包含 2 KB 主栈、512 B 传统 heap、10 KB FreeRTOS heap 与全部全局变量。新增缓冲、任务或栈都可能直接导致链接失败或运行时栈溢出；改完必须重新看 `.map`。

### 9.2 无绝对航向，yaw 会漂移（高）

没有磁力计或 GPS，yaw 以起飞瞬间为参考；静止标定只能减小固定零偏，温漂造成的长期漂移无法从原理上消除。上升段保持的是相对 yaw，不是地理航向。

### 9.3 引导模型简化（中高）

只有像素视线角，没有距离、速度与闭合速度，属于静止目标下的前视追踪；未建模相机延迟、畸变、安装角与滚转引起的图像旋转。前视时间与速率死区需要实机整定，焦距与视线偏置需要标定。

### 9.4 没有着陆 / 结束状态（中）

进入 `DESCENT` 后不会退出。落地后若仍有视觉帧会继续打舵；目标失效只回中，没有“已落地”判定、搜索或失控保护。

### 9.5 录像吞吐与帧率（中）

原生 RGB565 每帧约 154 KB。按 30 FPS 估算写入约 4.6 MB/s，普通 SD 卡可能跟不上；写卡期间主循环被拉长，串口接收可能溢出，遥测与视觉帧都可能丢。

### 9.6 单字节中断接收（中）

115200 下满速约 11 520 次 IRQ/s，当前负载不高但中断频繁；高负载时可能丢字节，只能靠 CRC 与滑窗重新同步恢复。后续可改 USART DMA + IDLE。

### 9.7 握手依赖（中）

OpenMV 不握手就不进入主循环，单独调试视觉不方便；OpenMV 中途复位会触发重新握手；ACK 的 MODE 必须与 F103 的 `DART_MODE` 完全一致。

### 9.8 参数未整定（中）

22 m/s²、5 周期、300 ms、5°、25 周期、前视 0.20 s/±3.0° 已由 11.11 实测校核（yaw/roll 自稳可用，pitch 补偿成功率 6/8）；两套视觉 PID 与焦距仍未标定。起飞检测依赖去重力加速度，安装方向或符号错误会直接导致不触发或误触发。

### 9.9 舵机方向与混控未验证（高，安全）

四个舵机编号、正方向、机械零位与混控符号必须拆动力逐轴确认。单周期 30 µs 步进会掩盖瞬态方向错误，测试时要观察完整行程。

### 9.10 BMI088 标定阻塞（中）

单轮 6000 点、带延时，约数秒；条件不满足会持续重试。标定期间 `imu_ready = 0`，控制任务直接返回。上电必须静止，否则零偏错误。

### 9.11 工程卫生（中）

`Control_Task.c`、`ctl_task.h`、`controller.c`、`BMI088driver.c` 仍为 GBK，其余多为 UTF-8；工程内保留大量未参与编译的 RoboMaster 框架代码（`ui.c`、`judge_protocol.c`、`drv_can.c`、`Correspondence_Task.cpp` 等），阅读时应直接跳过。

### 9.12 其他

- USB PCD、USART3、TIM3 的初始化已从 `main()` 删除，但对应源文件仍参与编译。
- `VISION_ERROR` 会覆盖遥测 state 但不改变真实状态，排查时看 flags 与 P/Y/R。
- `T` 持续增加但 YPR 不变，说明遥测在收、IMU 未更新；`T` 停止增加，查串口、供电或 SD 写入。
- `main.py` 使用 `sensor` + `pyb.UART`，回放脚本使用 `csi`，两者依赖具体 OpenMV 固件版本。

## 10. 排障手册

| 现象 | 可能原因 | 检查 |
|---|---|---|
| OpenMV 一直 `waiting handshake...` | F103 未上电/未烧录；PA9 未接 | 量 PA9 波形；确认 F103 LED 至少蓝色；确认 `openmv_handshake_send()` 被调用 |
| 握手成功但屏幕 `P:--` | 未 armed；遥测被截断；接触不良 | 确认收到 ACK；逻辑分析仪看 37 B 帧；检查 `huart1.gState` |
| `L:0` 且角度 `--` | 300 ms 内无有效遥测 | 检查波特率、CRC、接线、F103 是否在发 |
| `T` 增加但 YPR 不变 | 遥测在收、IMU 未更新 | 看 GX/GY/GZ；查 BMI088 初始化、标定、SPI |
| `T` 不增加 | 接收停、缓冲溢出、供电跌落 | 查 SD 写入、串口错误回调、电源 |
| `V:1` 但无 `Found!` | 有帧但未识别目标 | 查阈值、光照、目标颜色、ROI |
| 有 `Found!` 但飞控无反应 | 偏移超范围、CRC 错、单轴置零 | 看 dx/dy 是否在 ±160/±120；查 CRC；确认 mode |
| 不录像 | 未收到状态 3..5；SD 不可写 | 看 `record start:`；查 `RECORD_DIR`；确认遥测 state |
| `record open fail` | SD 未挂载 / 只读 / 编号耗尽 | 换卡、格式化为 FAT、清理旧录像 |
| 录像文件很大 | 原生 RGB565 未压缩 | 正常；用回放脚本导出 MJPEG |
| 回放找不到录像 | 不在搜索目录；文件名不符 | 看脚本列出的目录；设 `STREAM_PATH` |
| `Cannot open ImageIO recording` | 文件损坏或不是 ImageIO 格式 | 确认是当前 `main.py` 所录；检查文件头 |
| 导出 MJPEG 失败 | 输出已存在 | 改名或删旧 `.mjpeg` |
| Keil 编译报错 | 器件包缺失、路径变化、编码被改 | 按本机 Pack 配置；确认 GBK 文件未被转 UTF-8 |
| 舵机不动 | PWM 未启动、舵机未就绪、供电不足 | 看是否到 `SERVO_READY`；量 PA0–PA3；单独供电 |
| 舵机方向反 | 轴符号、混控、接线 | 拆动力，逐轴改 `DART_*_OUTPUT_SIGN` 或混控 |
| 起飞不触发 | 阈值太高、方向反、加速度未去重力 | 看 `MotionAccel_b[0]`；确认 `DART_LAUNCH_X_SIGN` |
| 提前进入下降 | pitch 噪声、阈值、确认数太小 | 看 P 曲线；加大确认数或调整阈值 |
| 下降段乱打舵 | 目标无效、引导过强、符号错 | 看 flags bit1；降低 N 与限幅；查相机符号 |
| 上电反复标定 | 机体未静止、振动 | 静止放置；查陀螺零偏条件 |
